# Working with S3 in DuckDB GraphAr

## Overview

When a GraphAr graph is stored on S3, the extension reads it through
[Apache Arrow's](https://arrow.apache.org) S3 filesystem. Authentication data is
pulled from environment variables, **not** from DuckDB's `CREATE SECRET`:

```
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
AWS_DEFAULT_REGION
AWS_ENDPOINT_URL
AWS_ENDPOINT_URL_S3
```

Set both `AWS_ENDPOINT_URL` and `AWS_ENDPOINT_URL_S3` to the same value. They
are aliases for the S3 endpoint (`AWS_ENDPOINT_URL_S3` takes precedence when
both are set); setting both to the same endpoint is the simplest setup that
always works. Do not leave them unset — otherwise Arrow falls back to resolving
the bucket region against AWS (a `HeadBucket` request), which is wrong for a
non-AWS endpoint and can crash the process (`free(): invalid pointer`).

To build the DuckDB-side secret you also need the `httpfs` extension (it provides
the `config` secret provider used below, and is enough for `getenv` in `CREATE
SECRET`). `aws` is only required if you want DuckDB to use the `credential_chain`
provider; it is **not** needed for the setup shown here.

## Local usage example

Assumes `./duckdb` is a DuckDB binary with the DuckDB GraphAr extension
pre-installed.

### 1. Set environment variables

```bash
export AWS_ACCESS_KEY_ID=...
export AWS_SECRET_ACCESS_KEY=...
export AWS_DEFAULT_REGION='us-east-1'
export AWS_ENDPOINT_URL='https://s3.example.com'
export AWS_ENDPOINT_URL_S3='https://s3.example.com'
```

### 2. Start DuckDB

```bash
./duckdb
```

### 3. In the DuckDB console

```sql
-- Load the required extensions
INSTALL httpfs;
LOAD httpfs;

-- Create the S3 secret
CREATE OR REPLACE SECRET secret (
    TYPE s3,
    PROVIDER config,
    KEY_ID getenv('AWS_ACCESS_KEY_ID'),
    SECRET getenv('AWS_SECRET_ACCESS_KEY'),
    REGION getenv('AWS_DEFAULT_REGION'),
    ENDPOINT getenv('AWS_ENDPOINT_URL')
);

-- Done! Now work with S3. Example:
ATTACH 's3://path/to/graphar/Graph.yaml' (type duckdb_graphar);
```

## Finalizing S3 at shutdown

Arrow requires `FinalizeS3()` to be called before the process ends, otherwise it
may print

```
arrow::fs::FinalizeS3 was not called even though S3 was initialized. This could
lead to a segmentation fault at exit
```

and segfault at exit. The extension now performs this teardown **automatically**:
a DuckDB `ExtensionCallback` registers an `OnConnectionClosed` hook that calls
`graphar::FinalizeS3()` (guarded by `arrow::fs::IsS3Initialized()` &&
`!arrow::fs::IsS3Finalized()`) when a connection closes. You do **not** need to
call anything by hand for correct shutdown.

The `duckdb_graphar_finalize_s3()` SQL function is still available:

```sql
SELECT duckdb_graphar_finalize_s3();
```

### Important: `finalize_s3()` is terminal

`finalize_s3()` is a **one-way, terminal** operation. It means "I am done using
Arrow S3 for the rest of this process's lifetime". Any S3 access **after** it
(for example a second `SELECT`, a catalog scan, or another `ATTACH`) aborts the
process with `Attempt to initialize S3 after it has been finalized`.

Therefore, even though teardown is now automatic, do **not** call
`duckdb_graphar_finalize_s3()` mid-session and then keep reading:

- **Do not** call `finalize_s3()` after `ATTACH` and then keep reading.
- In a long-lived process that keeps reading the graph, do **not** call it until
  the process is being shut down.
- Call it only as the **last** S3 statement, right before the process exits (and
  it is safe to omit entirely thanks to the automatic teardown).
